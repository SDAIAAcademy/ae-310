Session 1

Prompt, retrieve, tune or distil

  • Name what prompting, retrieval, tuning and distillation each change in a system
  • Sort the failures of a prompted model into knowledge, format and behaviour
  • Assign each failure class to an approach, with counts
01
Four ways to change what a model does

Each lever changes a different part of the system

Prompt

Changes the instructions. Minutes to try, read again on every request.

Retrieve

Changes what the model is shown: a table, a document, a record.

Tune

Changes the weights, from your examples. Days of work, then no extra tokens.

Distil

Tuning whose examples come from a larger model.

Order of cost. Try them left to right. Each one you skip is a cheaper fix you never tested.

The durable idea of the day: adapt only after a stronger prompt fails. Ask who has seen a team fine-tune a model to fix something a schema hint would have fixed. Distillation is a kind of tuning; it gets its own card because where the examples come from changes the licence question (session 3) and the errors you inherit (Day 3).

What tuning is good at

Tuning changes behaviour more than knowledge

Tuning teaches well

  • a format, exactly and every time
  • which tool to choose
  • when to stop and hand over to a person
  • a register, a language, a house style

Tuning teaches badly

  • facts that change: a code table, a fee, a deadline
  • facts seen once in the training set
  • anything you must be able to correct tomorrow

A fact in the weights cannot be edited, cited or dated. A fact in the context can.

Use the chamber's activity codes: twelve codes, revised every year. A tuned model can memorise twelve rows, and in January it will still answer with last year's. The course's own small model does memorise them, and Day 4 names that as a limit. Rule of thumb for the room: if the fix is "the model should know X", think retrieval; if it is "the model should do Y", think tuning.

Where a small model belongs

Small models suit narrow tasks, not multi-step work

A small tuned model fitsIt does not fit
One request in, one structured answer outA plan of several steps that depend on each other
A fixed set of tools and fieldsTools it has never seen
Thousands of similar requestsRare requests that each need judgement
An answer a program can checkAn answer only an expert can check
Qayd is on the left. One request, one of five tools, fields a schema can verify. The rare and the odd go to the registry desk through escalate_to_staff.

The LFM3-1.7B model card says the same of its own model in its own words: designed for tool calling and fine-tuning, not recommended for complex multi-step reasoning. A small model that escalates well is worth more than one that tries everything.

Sources: LFM3-1.7B model card.

The task, once

One request in, exactly one tool call out

memberWe moved our head office to Abha. Please update the record of CR 4064749760. Our partner company holds CR 4071506418; do not change their record.
tool call{"name": "update_record", "arguments": {"cr_number": "4064749760", "field": "city", "value": "Abha"}}
graded by codethe same tool and the same arguments as the correct call, or it is wrong

Five tools: create_membership, renew_membership, update_record, issue_certificate, escalate_to_staff.

Read the request aloud and ask what could go wrong. Collect answers: the partner's number, Arabic-Indic digits, a code fence around the JSON, renewing instead of updating, no number at all. Every one of those is planted in the data. Exact match is strict on purpose: the registry service will not accept a nearly right call.

Session 2

The baseline tuning must beat

  • Improve a prompt with schema hints, context and examples, one change at a time
  • Report a score on 100 requests with an interval
  • Freeze a baseline: the prompt, the set and the score
02
The most common false result in fine-tuning

A weak prompt flatters tuning

  • "Our tuned model went from 27 to 85" compares a week of work with one careless sentence
  • Half of that gain may be available in an afternoon, with no training at all
  • The honest comparison is against the best prompt you could write

What the baseline is for

It is the number the adapter must beat on Day 4. If the adapter cannot beat a good prompt on the same model, the project ends here, cheaply.

This is the first durable idea in the entry: adapt only after a stronger prompt fails. Ask: who decides that the prompt is "the best you could write"? Nobody can prove it. What you can do is show the steps you took, one change at a time, with scores. That record is what a reviewer accepts.

Method

One change at a time, each scored on the same 100 requests

v0one sentence
→
v1schema hints
→
v2the code table
→
v3the rules
→
v4four examples
Each change targets a class. Schema hints: format. The table: knowledge. Rules and examples: behaviour, as far as words can reach it.

Prompts as versioned code is AE-203, day 1; nothing new there. What is new is the purpose: the versions are an argument. Each step shows which class of failure words alone can remove.

Version 1

A schema hint tells the model what a call looks like

Answer with exactly one tool call and nothing else, in this form: <tool_call> {"name": "<tool>", "arguments": {...}} </tool_call> Tools: create_membership(company_name, cr_number, city, activity_code) … escalate_to_staff(reason) cr_number is 10 Western digits (convert Arabic-Indic digits). company_name is copied as written. city is the English name.
The wrapperThe interfaceHow to write each field

Each sentence answers a failure seen in Lab 1.1: prose and code fences (the wrapper), wrong key names (the interface), digits and translated names (the field rules). A server can also force the form with constrained decoding; that removes parse errors, not wrong decisions, and it must then be used in training and serving alike.

Version 4

Examples come from validation requests, never from the test set

Validation set

120 requests. The source of the four examples, and of every choice on Day 3.

The 100 requests

Analysis and the baseline score. An example taken from here is an answer shown in advance.

Test set

400 requests from companies no other set contains. Opened on Day 4, once.

No personal data in an example. An example is sent with every request, for as long as the prompt lives.

The split is by company: no company of the test set appears in the traces, the pool or the validation set. Day 2 shows what happens when that is violated (23 planted leaks). The four examples were chosen to cover a new membership, an Arabic certificate request, a missing number and an out-of-scope question, and none carries a contact line.

How sure is 67 out of 100

A score on 100 requests carries an interval of about ±10 points

57 to 75
95% Wilson interval for 67 right out of 100
  • v2 scored 50 and v3 scored 52: two requests apart, well inside the noise
  • The interval answers "what would another hundred requests give?"
  • It does not compare two versions: the versions ran on the same requests, and Day 4 uses that pairing

Participants know a paired test from the prerequisites. Here the point is smaller: never write a score without its n and its interval. In the lab they write the Wilson formula themselves; the check value is 50 of 100 giving 0.404 to 0.596.

What "frozen" means

A baseline is three things that never change again

The instructions

Identified by a hash of their text and examples. One edited sentence is a new baseline.

The set

The same file of requests, by name and by content.

The score

Right answers, n, and the interval. Recorded with the model's name and the day.

{"prompt_sha256": "bdf86a63…", "n": 100, "correct": 67,
 "accuracy": 0.67, "interval": [0.573, 0.754],
 "set": "data/requests_100.jsonl"}

The file is small and it ends arguments. On Day 4, when someone asks "better than what?", this is the answer. In the capstone the baseline file is committed before any training log, and the timestamps show it.

The case for tuning, stated honestly

What the best prompt leaves behind is behaviour

  • The schema is there, the table is there, the rules are written
  • The model still takes the partner's number, still renews where it should escalate
  • The larger model, same words: 94. Room above the baseline: 27 requests in 100
Now tuning has a target. Not "make it better": remove the behaviour failures that 33 requests in 100 still show, and reach towards 94.

If the residue had been small, the right decision would be to stop: ship the prompt. Say this explicitly. A course on adaptation must be willing to conclude "do not adapt". The capstone rubric gives full marks for a well-argued decision not to tune, if the baseline evidence supports it.

Session 3

Licences and terms of open-weight models

  • Distinguish permission to adapt, to deploy and to distribute in a model licence
  • Find conditions that depend on who deploys and for what
  • Record which candidate models the chamber may adapt and deploy
03
Before any training

"Open weights" means you can download it, not what you may do with it

  • Every model on the Hub has a licence file. The tag on the card is a label someone typed
  • Licences differ on purpose, on revenue, on field of use and on what you pass on
  • The check costs an hour before training and a project after deployment

Who decides

You find the clause and the fact it depends on. Zakariya Al-Mousa, the chamber's counsel, decides. "Ask counsel" is a valid entry in your table.

The entry lists "licences before training" among the durable ideas, and model families and their licences among the things to refresh every run. The three sheets in the lab were read on the date written inside each; re-read the licence texts before the cohort. This session is not legal advice and says so: it trains engineers to bring counsel the right question.

Read a licence with three questions

Adapt, deploy and distribute are three separate permissions

Adapt

Fine-tune it. The result is a derivative work in most licences.

Deploy

Run it in a service. Here licences ask for what purpose and by whom.

Distribute

Give the weights or the adapter to someone else. Conditions travel with it.

The chamber's plan needs all three: tune on its requests, run inside a service members pay fees for, give the adapter to two sister chambers.

Most restrictive licences allow adapting for research and restrict the other two. Teams discover this after training, when the adapter exists and cannot be used. Whether an adapter alone is a derivative work is a question licences answer differently: one more reason to read the text.

A licence table without facts is an opinion

Two conditions turn on facts about the chamber

The revenue threshold

The chamber's annual revenue is SAR 62 million, which is USD 16.5 million: above the threshold. Its use is licensed only if it is not "commercial use".

The purpose

The chamber is a non-profit body, and its service charges fees. Is that "primarily intended for commercial advantage or monetary compensation"? The text does not say.

Write the question down now. "Ask" in the table, with the clause and the fact, is a result. Finding out after deployment is not.

The chamber's revenue and legal form are fictional facts of the case, in data/chamber_facts.json. The conversion uses SAR 3.75 to the dollar. Make the room argue both sides of the fee question for two minutes; they will not agree, and that is the point: the engineer's job is to surface the question with its clause.

Three habits

Read the text, record the day, look for a second document

  • The text, not the tag. Open the licence file in the repository; a card can say "other" and hide everything
  • The day you read it. A later release of the same family can carry different terms
  • A second document. An acceptable-use policy, or conditions on a gated page, bind you as well
  • The teacher too. On Day 3 a larger model writes your training labels: its terms on using outputs to train another model belong in the same table

The fourth bullet is the one teams forget. Check whether the terms say anything about training another model on the outputs. The course's teacher is an open-weight model reached through a hosted API: both the model's licence and the API provider's terms apply. Have the room name the two documents they would check.

Session 4

Cost and placement of the options

  • Estimate tokens and cost per request from measured requests
  • Compare a per-token price with an owned accelerator at a given volume

04
Two ways to pay for a model

A hosted model costs per token; an owned accelerator costs per month

Hosted

  • a price per million input and output tokens
  • cost grows with volume, starts at zero
  • the request leaves your servers

Owned

  • purchase over its useful life, power, an engineer's hours
  • the same cost at one request or a million
  • the request stays where you put the machine
Cost per thousand requests is the unit that makes them comparable, and for the owned machine it depends entirely on volume.

AE-205 covers sizing and cost of a service in general. The addition here is the token: a prompted model pays for its instructions on every request, a tuned model does not. Keep the room to the two options the entry names: a large hosted model, and a tuned small model on the chamber's own accelerator.

Three costs, three shapes

Tuning is paid back in quality, not money. A prompted and a tuned small model cost the same to serve on the same machine. And the engineer costs more than the GPU.

Almost all of the one-off cost is the engineer's time building the data (Day 2), not the GPU hours. That is the realistic proportion, and it is why the rubric gives data quality 25 points and training 15. Every retraining pays the one-off cost again, in part: plan for it when the request mix changes.
